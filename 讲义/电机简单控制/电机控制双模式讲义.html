二、电机驱动基础知识铺垫

2.1 电机驱动三信号

信号端口电平逻辑作用
PWM（驱动）P4.6低=驱动，高=惯性停控制电机是否通电
DIR（方向）P3.7高=正转，低=反转控制转动方向
BRAKE（刹车）P4.7低=刹车，高=松闸快速制动

2.2 动作顺序（关键安全规则）

⚠️ 动作顺序不能乱
  • 启动：先松闸 → 设方向 → 再驱动（避免带电切换方向产生大电流冲击）
  • 停止：先停驱动 → 再刹车（避免驱动与刹车瞬间冲突）
  • 上电默认：惯性停转状态（BRAKE=1, PWM=1, DIR=1），上电不启动

2.3 PWM 恒定电平驱动（教学简化）

本项目 PWM 不生成方波波形，只输出恒定电平：低电平=全速驱动，高电平=惯性停止。 这样无需配置定时器，面向初学者大幅简化。后续如需调速可改为 PWM 方波输出。

2.4 两种按键检测方式

方式函数含义适用场景
放开事件Key_Sx_Released()检测"按下后松开"的完整动作自动模式（按一下切换状态）
电平检测Key_Sx_Down()检测当前是否按住点动模式（按住有效，松开停止）

三、与 AI 对话的核心原则

本次电机控制开发过程中，以下 5 条原则贯穿始终：

💡 五条核心原则
  • 原则 1：模块化思维 — 先要驱动模块再要主程序，AI 会自动分离 hardware 和 user 层，接口放 .h 实现放 .c
  • 原则 2：明确引脚 — "PWM=P4.6, DIR=P3.7, BRAKE=P4.7" 直接指定，避免 AI 自行分配造成冲突
  • 原则 3：增量叠加 — 每轮"在当前功能基础上继续加上…"，AI 在现有代码上叠加而非重写
  • 原则 4：简化优先 — 觉得复杂时直接说"太复杂，先做简化版"，AI 去掉工程约束保留核心逻辑
  • 原则 5：逐步加约束 — 理解核心后再说"加回工程安全约束"，AI 逐条补充并解释每条的意义
1
创建电机驱动模块（motor.h / motor.c）
目标：封装电机四种动作，建立 hardware/user 分层架构
🙋 用户提问
"加入电机控制模块，PWM=P4.6, DIR=P3.7, BRAKE=P4.7，实现正转、反转、惯性停转、刹车停转。给初学者用，逻辑简单清晰。"
🤖 AI 响应要点
  • 创建 hardware/motor.h（接口声明）和 hardware/motor.c（端口实现），建立分层架构
  • 用 sbit 定义三个端口，Motor_Init() 配准双向口 + 上电默认惯性停转
  • 四个函数严格按动作顺序：启动=松闸→设方向→驱动；停止=停驱动→（刹车）
  • PWM 用恒定电平而非方波，简化设计避免定时器配置
/* motor.c — 四个动作函数 */
void Motor_Forward(void) {
    BRAKE = 1;  DIR = 1;  PWM = 0;  /* 松闸→正转→驱动 */
}
void Motor_Coast(void) {
    PWM = 1;  BRAKE = 1;           /* 停驱动→松闸（惯性滑行） */
}
void Motor_Brake(void) {
    PWM = 1;  BRAKE = 0;           /* 停驱动→刹车（快速停） */
}
💡 对话技巧分析
  • "加入电机控制模块" — "模块"一词让 AI 自动采用 .h/.c 分离的模块化架构，而非把代码塞进 main.c。这是嵌入式工程的基本素养
  • 明确三个引脚 — "PWM=P4.6, DIR=P3.7, BRAKE=P4.7" 直接指定引脚，AI 不需要自行分配，避免与已有按键引脚冲突
  • "正转、反转、惯性停转、刹车停转" — 列出全部四个动作，AI 据此设计四个函数。注意"惯性停转"和"刹车停转"是两个不同的物理过程
  • AI 主动按动作顺序写代码（松闸→方向→驱动），并注释解释"避免大电流冲击"。这种工程细节是 AI 作为"有经验开发者"的体现
📝 教学启示

这一步的核心是模块化和动作顺序。学生应理解：① 电机驱动独立成模块， main.c 只调用接口，不直接操作端口——这是"高内聚低耦合"的入门；② 启动和停止有严格的端口操作顺序， 乱序会导致电流冲击或器件损坏。PWM 用恒定电平是教学简化，真实调速需 PWM 方波。

2
设计自动控制主程序（S4正转/S5停止/S6反转）
目标：用放开事件检测实现自动模式的电机控制
🙋 用户提问
"设计主程序 main 函数，S4 正转、S5 惯性停转、S6 反转，用放开事件检测。"
🤖 AI 响应要点
  • 用 Key_Sx_Released() 检测放开事件（按下再松开才算一次完整操作）
  • 引入状态变量 state：0=停止，1=正转，2=反转，按键动作时同步更新
  • 主循环三段式：检测按键 → 执行动作 → 更新状态
while (1) {
    if (Key_S4_Released() == 1) {
        Motor_Forward();  state = 1;
    }
    else if (Key_S6_Released() == 1) {
        Motor_Reverse(); state = 2;
    }
    else if (Key_S5_Released() == 1) {
        Motor_Coast();   state = 0;
    }
}
💡 对话技巧分析
  • "放开事件检测" — 明确指定用 Released 而非 Down。自动模式下"按一下切换状态"，需要完整的按下-松开动作，避免长按重复触发
  • AI 引入 state 变量记录电机状态——这是状态机思想的开始。后续双模式、限位保护都建立在这个状态变量之上
  • 用 else if 而非三个独立 if，保证同一时刻只响应一个按键，这是简单的互锁
📝 教学启示

这一步引入了两个核心概念：① 放开事件 vs 电平检测——自动模式用 Released（按一下算一次）， 点动模式用 Down（按住有效），选择哪种取决于交互需求；② 状态变量——程序行为不仅看按键， 还看当前状态，这是状态机的入门。学生应对比两种检测方式的差异。

加 OLED 显示（人机界面）
目标：OLED 显示标题和运行状态，建立人机界面
🙋 用户提问
"加 OLED 显示，第一行'电机控制系统'，第二行'运行状态：正转/反转/停止'。"
🤖 AI 响应要点
  • 标题和标签开机画一次，状态文字由主循环每帧根据 state 刷新
  • 用 OLED_ShowChinese 显示中文，OLED_ShowMixedText 显示"中文+冒号"混合
  • 验证字库包含"电机控制系统""运行状态""正转""反转""停止"等全部汉字
/* 开机画固定界面 */
OLED_ShowChinese(24, 0, "电机控制系统");   /* 第一行：标题 */
OLED_ShowMixedText(0, 16, "运行状态:");     /* 第二行：标签 */
OLED_ShowChinese(72, 16, "停止");           /* 初始状态 */

/* 主循环刷新状态文字 */
if (state == 1)      OLED_ShowChinese(72, 16, "正转");
else if (state == 2) OLED_ShowChinese(72, 16, "反转");
else                OLED_ShowChinese(72, 16, "停止");
💡 对话技巧分析
  • "第一行…第二行…" — 直接给出界面布局，AI 据此计算坐标（中文16×16，5字标题居中x=24，标签+冒号占72px，状态从x=72开始）
  • 固定内容开机画一次 — 标题"电机控制系统"和标签"运行状态:"不变，开机画一次即可。主循环只刷新变化的状态文字，这是显示效率优化
  • AI 主动验证字库，确认所有汉字都有字模不会乱码。这种前置检查避免了运行时才发现缺字的问题
📝 教学启示

这一步建立了人机界面的基本框架：固定内容（标题/标签）开机绘制，动态内容（状态文字）循环刷新。 学生应理解：OLED 显示的本质是往显存写数据再 Update 上屏，固定内容不需要每帧重写，只刷新变化的部分即可。 这种"静态画一次 + 动态循环刷"的策略贯穿后续所有显示设计。

4
设计点动控制（按下驱动，放开停止）
目标：用电平检测实现点动——按住转动，松开停止
🙋 用户提问
"设计点动控制（手动模式），按下正转键正转，放开惯性停止。"
🤖 AI 响应要点
  • 用 Key_Sx_Down() 电平检测：返回1=当前按住，0=未按住
  • S4 按住→正转，S6 按住→反转，都不按或都按→惯性停止
  • 与自动模式的差异：自动用 Released（按一下切换），点动用 Down（按住有效）
/* 点动模式：电平检测 */
unsigned char s4 = Key_S4_Down();
unsigned char s6 = Key_S6_Down();
if (s4 == 1 && s6 == 1) {      /* 同时按下 → 停止 */
    Motor_Coast();  state = 0;
}
else if (s4 == 1) {            /* 按住S4 → 正转 */
    Motor_Forward(); state = 1;
}
else if (s6 == 1) {            /* 按住S6 → 反转 */
    Motor_Reverse(); state = 2;
}
else {                        /* 都没按 → 停止 */
    Motor_Coast();  state = 0;
}
💡 对话技巧分析
  • "按下…放开…" — 这个描述精确对应电平检测：按下=Down()返回1，放开=返回0。AI 准确选择了 Key_Sx_Down() 而非 Released
  • 同时按下处理 — AI 主动加了 s4 && s6 的判断，两个方向键同时按住时强制停止。这是简单的互锁保护，避免驱动逻辑矛盾
  • else 分支惯性停止 — 都没按时执行 Motor_Coast()。这意味着主循环每帧都在判断：按住就驱动，松开就停。这就是"点动"的精髓
📝 教学启示

这一步的核心是两种按键检测方式的对比。自动模式用 Released（放开事件，按一下切换状态）， 点动模式用 Down（电平检测，按住有效松开停止）。学生应动手对比：同一个 S4 键，在自动模式下"按一下正转一直转"， 在点动模式下"按住才转松开就停"。这就是交互模式的差异——同一个硬件，不同的软件逻辑，完全不同的操作体验。

5
整合双模式（S7 切换自动/点动）
目标：S7 切换两种模式，OLED 第三行显示当前模式
🙋 用户提问
"整合自动和点动两种模式，S7 切换模式，第三行显示模式，加工程安全约束：不能直接换向、运动时不能切换模式、多键互锁。"
🤖 AI 响应要点
  • 新增 mode 变量：1=自动，0=点动；S7 放开事件翻转 mode
  • 主循环按 mode 分发：if (mode==1) 走自动逻辑，else 走点动逻辑
  • 第三行显示"当前模式：自动/点动"
  • 三条工程约束：① 方向互锁 ② state==0 才能切模式 ③ 同时按下互锁
/* S7 切换模式：仅停止时可切换 */
if (Key_S7_Released() == 1) {
    if (state == 0) {            /* ← 工程约束：运动中不能切 */
        mode = !mode;
    }
}

/* 按 mode 分发控制逻辑 */
if (mode == 1) { ... }  /* 自动模式 */
else { ... }          /* 点动模式 */
💡 对话技巧分析
  • "整合…S7切换…加工程安全约束" — 一句话包含三个需求：整合、切换、约束。AI 分三条实现：mode 变量、S7 逻辑、三条 if 检查
  • 两个状态变量 — mode（管"用哪套逻辑"）和 state（管"电机当前状态"）。AI 准确理解了这两个变量的独立性，没有混淆
  • 三条约束一次给全 — 用户直接列出三条工程约束，AI 逐条翻译成 if 条件。这种"需求清单"式的描述让 AI 不遗漏
📝 教学启示

这一步是状态机的进阶。程序现在有两个独立状态变量：mode 和 state。 主循环先看 mode 决定走哪套逻辑，再看 state 决定能否执行操作。学生应理解：① 模式分发—— 用 if-else 按 mode 走不同分支，是状态机的典型结构；② 工程约束——"运动中不能切模式" 翻译成 if (state==0)，"不能直接换向"翻译成 if (state != 2)，业务规则变成 if 条件。

6
简化版 → 工程约束版迭代
目标：先去约束理解核心，再加回约束学习工程
🙋 用户提问（简化）
"太复杂了，先做简化版，不考虑工程约束。"
🤖 AI 响应要点
  • 去掉三处安全检查：S7 直接翻转 mode、方向键直接执行、点动用简单 if-else if-else
  • 保留核心：mode 和 state 两个标志位构成的状态机
  • 代码量减少约 30%，逻辑更直白，适合初学者理解状态机流转
🙋 用户提问（加回约束）
"现在加回工程安全约束。"
🤖 AI 响应要点
  • 逐条加回：① if (state==0) 才能切模式 ② if (state!=2) 才能正转 ③ s4&&s6 同时按下停止
  • 每条约束都加注释解释"为什么"——不能直接换向（避免大电流）、运动中不能切模式（避免失控）
💡 对话技巧分析
  • "太复杂了，先做简化版" — 这是教学策略的关键决策。初学者面对状态机+工程约束会注意力分散，先去约束理解核心，再加约束学工程。AI 立即执行，不"坚持己见"
  • "现在加回工程安全约束" — 理解核心后，一句话加回全部约束。AI 逐条补充并注释解释每条的意义。这种先减后加的教学节奏由用户掌控
  • 简化版 vs 工程版对比 — 简化版 S7 直接翻转 mode，工程版加 if(state==0)。学生通过对比能清楚看到"约束就是加 if 检查"，消除对"工程约束"的畏惧
📝 教学启示

这一步展示了简化优先的教学策略。面对复杂系统，先去掉约束让学员理解核心状态机流转， 再逐步加回约束学习工程思维。这比一步到位给出完整工程代码更有效——学员不会"一上来就懵"。 学生应理解：工程约束的本质就是加 if 检查——"运动中不能切模式"就是 if(state==0)， "不能直接换向"就是 if(state!=2)。业务规则 → if 条件，这就是编程。

十、AI 对话经验总结

10.1 有效的提问模式

📌 模块化开头

"加入电机控制模块" — AI 自动 .h/.c 分离，建立分层架构

📌 明确引脚

"PWM=P4.6, DIR=P3.7" — 指定引脚，避免冲突

📌 指定检测方式

"放开事件检测" vs "按下…放开…" — 选 Released 还是 Down

📌 描述界面布局

"第一行…第二行…" — AI 自动计算坐标和字库

📌 简化优先

"太复杂，先简化" — 去约束理解核心，AI 立即执行

📌 逐条加约束

"加回工程约束" — AI 逐条补充并注释解释

10.2 AI 协作的优势与局限

方面AI 的优势需要注意的局限
模块设计 自动 .h/.c 分离，sbit 定义端口，动作顺序符合工程规范 需用户指定引脚，AI 不会自行分配（避免冲突）
状态机 引入 mode/state 变量，按模式分发逻辑，结构清晰 复杂约束需用户分条列出，AI 不会主动"猜"业务规则
显示设计 固定内容画一次+动态循环刷，自动验证字库 缺字时需用户授权"做字库"，AI 才会主动生成字模
教学简化 能按指令去掉/加回约束，保留核心逻辑 需用户判断"何时简化何时加回"，AI 不会自行决定教学节奏

10.3 给学生的建议

📝 四条核心建议
  • 建议一：先模块后系统 — 电机驱动独立成模块，main 只调用接口。不要把端口操作散在 main 里，这是"高内聚低耦合"的入门
  • 建议二：理解两种检测方式 — Released（放开事件，按一下切换）和 Down（电平检测，按住有效）是两种根本不同的交互。自动模式用前者，点动模式用后者
  • 建议三：状态机=变量+分发 — mode 和 state 两个变量，if-else 按 mode 分发逻辑，这就是状态机。不要畏惧"状态机"这个词，它就是"看变量走不同分支"
  • 建议四：工程约束就是加 if — "不能直接换向"就是 if(state!=2)，"运动中不能切模式"就是 if(state==0)。业务规则变成 if 条件，这就是工程编程。先理解核心再加约束，不要一上来就追求"完整工程版"
