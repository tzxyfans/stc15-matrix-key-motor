二 核心问题：为什么"电平式"数不出次数

上一讲的 Key_S4_Down() 只回答"现在按着吗"。如果直接拿它计数，按住 1 秒 = 1000ms ÷ 20ms = 50 帧 = 计数器狂加 50 次。想数"按了几下"，必须换一种问法。

（一）两种"问法"的根本区别

对比项 电平式 Key_S4_Down() 事件式 Key_S4_Released()
回答的问题"S4 现在被按着吗？""S4 刚完成了一次完整的按下→松开吗？"
返回 1 的时机按住期间每一帧都返回 1整个按住过程只在松开的那一帧返回 1
按住 1 秒连续返回 50 个 1只在第 50 帧返回 1 个 1
拿来计数错误按 1 次 → 加 50正确按 1 次 → 加 1
适合干什么实时状态显示（本讲仍在用）计数、触发一次性动作
需要的"装备"读一次引脚电平即可额外需要 static 变量记住"上一次状态"

（二）用波形图看懂"边沿"

（三）为什么选择在"松开"时计数，而不是"按下"时

⏬

按下沿（下降沿）计数

last == 1 && now == 0

手指刚触到按键就 +1。响应"快"，但如果手一抖刚碰到又弹开，也算了一次——事件的"确认感"弱。

⏫

松开沿（上升沿）计数 ← 本项目采用

last == 0 && now == 1

手指按下并松开才 +1。一次完整动作 = 一个句号，语义最接近"按了一下"，也符合人们使用遥控器、键盘的习惯。

💡 一句话记住："按了几下"数的是边沿（状态跳变）的个数，不是电平的持续时间。抓住边沿，靠的是记住上一次的状态——这正是下一章计数变量和第四章 Released 函数各自扮演的角色。

三 计数变量的定义：给每个按键发一本"账本"

要计数，先得有个地方"记账"。main.c 顶部四行看似平平无奇的变量定义，其实每一个关键字都是精心选择的。

（一）代码原文

/* 定义在 main.c 顶部、所有函数之外 —— 全局变量区 */
unsigned char count_s4 = 0;   /* S4 按下次数（0~99，计数至 100 清零） */
unsigned char count_s5 = 0;   /* S5 按下次数 */
unsigned char count_s6 = 0;   /* S6 按下次数 */
unsigned char count_s7 = 0;   /* S7 按下次数 */

（二）逐个关键字的"为什么"

1️⃣ 为什么用 unsigned char？

本项目的计数范围是 0~100，unsigned char（无符号字符型）取值 0~255，一个字节就够用。STC15 内部 RAM 只有 256 字节，"能省一个字节就省一个字节"是嵌入式的基本素养。

候选类型范围 / 占用结论
bit0 ~ 1（1 位）不行只能记"有没有"，数不了次数
unsigned char0 ~ 255（1 字节）首选覆盖 100，最省内存
unsigned int0 ~ 65535（2 字节）能用但计不到 255 就清零了，白占 1 字节
2️⃣ 为什么定义在函数外面（全局变量）？

计数值必须在两次主循环之间"活着"：这一帧加到 12，下一帧要在 12 的基础上继续。全局变量的生命周期 = 整个程序运行期，存放于静态存储区，从头到尾不会被系统回收——正是一本随叫随到的"账本"。
反例：若把 unsigned char count_s4 = 0; 写进 while(1) 循环体内，每 20ms 进入新一轮循环时变量都会重新出生、归零——账本每 20ms 撕一页，永远数不起来。

3️⃣ 为什么要显式写 " = 0"？

C 标准保证：全局变量即使不初始化，也会自动清零（存放在静态存储区，上电默认全 0）。所以 = 0 可以省略——但显式写出来是好习惯：读代码的人一眼就知道"计数从零开始"，不依赖语言细节。

4️⃣ 为什么是四个独立变量，而不是一个数组？

本阶段以"看得懂"为第一目标：count_s4 与 S4 一一对应，直白清晰。下一讲做程序优化时，会把它升级成 count[4] 数组 + for 循环——先用笨办法理解本质，再用巧办法优化结构。

📌 计数器三要素之"账本"：变量定义 = 发账本。类型决定账本容量（能不能记到 100），作用域决定账本寿命（会不会中途被撕掉）。这两件事想清楚，计数器的地基就稳了。

四 按键按下并放开函数解读：抓住"松开的那一瞬间"

上一讲 key.c 里预埋的 Key_S4_Released() 本讲正式上岗。它只有短短几行，却是全项目的灵魂——先读代码，再逐帧"演"一遍它的工作过程。

（一）代码原文（带序号精讲）

static bit s4_last = 1;        /* S4 上一次按键状态（1 = 未按下），程序运行期间不丢失 */

unsigned char Key_S4_Released(void)
{
    bit now = S4;                      /* ① 读按键当前电平（1 = 放开，0 = 按下） */
    if (s4_last == 0 && now == 1)      /* ② 上次按下 + 本次放开 = 一次完整按键结束 */
    {
        s4_last = now;                 /* ③ 保存本次状态，供下一次比较 */
        return (1);                    /* ④ 事件成立，只在本帧返回一次 1 */
    }
    else
    {
        s4_last = now;                 /* ③' 没有事件也必须保存本次状态！ */
        return (0);                    /* ④' 无事件返回 0 */
    }
}

（二）四步拆解

①

读现在：bit now = S4

now = 1 → 松开；now = 0 → 按下

直接读引脚当前电平。注意与 Key_S4_Down() 不同——这里读的是"原始电平"，1 表示松开，不做取反。

②

比历史：s4_last == 0 && now == 1

上次按下 & 本次松开

两个条件缺一不可：只看"现在松开"不行（一直没人按也是松开）；只看"上次按下"也不行（还在按住中）。两者同时成立，才说明这一帧发生了"松开跳变"（上升沿）。

③

记账：s4_last = now

把"现在"变成下一帧的"过去"

无论事件是否成立，都要把本次状态存进 s4_last。这一行是函数的"记忆中枢"——没有它，程序每帧都失忆，永远抓不到跳变。

④

报事件：return 1 / 0

事件只闪现一帧

成立只可能出现在"松开后的第一帧"，下一帧 s4_last 已变成 1，条件自然不再成立——所以 1 只返回一帧、一次，计数就只加一次。

（三）逐帧"演"一遍：一次完整按键的全过程

假设 S4 在帧2 被按下、帧5 被松开（对照图 2-1 的波形），把每一帧函数内部的变化列成表：

帧号 now（本次电平） s4_last（上次状态） 条件 last==0 && now==1 返回值 执行后 s4_last 发生了什么
帧11（松开）1不成立01一直没人按，安静
帧20（按下）1不成立00刚按下（下降沿），不计数
帧30（按住）0不成立00按住中，无论多久都返回 0
帧40（按住）0不成立00同上
帧51（松开）0成立！11完整按键结束 → 计数 +1
帧61（松开）1不成立01恢复安静

（四）s4_last 的两个身份

🔒 身份一：static（模块私有）
外界谁也碰不到它
• 加了 static，作用域被锁死在 key.c 内部
• main.c 不知道、也不需要知道按键"历史状态"的存在
• 实现细节继续对上层的 main.c 隐藏
🧠 身份二：静态存储（长生不老）
函数返回后依然保留数值
• static 局部变量生命周期 = 整个程序运行期
• 函数每 20ms 被调用一次，s4_last 在两次调用之间不掉线
• 这正是它配当"记忆"的原因
⚠️ 最容易踩的坑：else 分支里的 s4_last = now 不能省！
  • 有同学觉得"只有事件成立才需要更新历史"——大错特错
  • 推演一下：帧2 按下（now=0），若 else 里不保存，s4_last 仍是 1；帧5 松开时判断 s4_last==0 不成立 → 事件永远检测不到，计数永远是 0
  • 记住口诀："不管有没有事，账每帧都要记"
💡 事件式检测的通用公式：事件 = (上次状态 A) && (本次状态 B)。A、B 取 0/1 的组合不同，得到的事件不同——"0→1"是松开沿（本讲用的 Released），"1→0"是按下沿（key.h 里已预告的 Key_Sx_Pressed()，课后练习等你实现）。这套"历史 + 现状"的边沿识别思想，以后在编码器测速、外部中断判沿、通信协议解析里会反复出现。

（三）三个使用要点

要点 说明
固定 Length = 3，高位自动补零 count = 12 显示 "012"，count = 7 显示 "007"。数字从 9 → 10 → 99 位数会变，固定 3 位后每次都画满 3 个字符，旧数字被自动覆盖，不需要清屏，绝不会残留。
Length 要罩得住最大值 本项目计数值最大到 99，Length = 3 绰绰有余。若 Length 比实际位数小（比如用 2 位去显示 100），高位会被截断、显示错乱——位数宁多勿少。
坐标 X 要预留像素预算 "N=" 两个字符，每个宽 8 像素，起点 x=72 → 占 72~87；数字紧跟其后从 88 开始，3 位 × 8 = 24 像素 → 88~111，距屏幕右边界 127 还有余量。排版就是做加法。
📌 别忘了两步写：OLED_ShowNum 与所有 Show 函数一样，只写显存、不上屏。真正让数字"晒"出来的是主循环末尾的 OLED_Update()——写显存（草稿）→ Update（上屏），这个机制本讲继续沿用。

六 次数上限的控制：100 次封顶与归零

计数器不能无限加下去：unsigned char 最多存 255，屏幕也只留了 3 位。本项目选择"计满 100 次自动清零"——三行代码，藏着计数器的"限幅"智慧。

（一）代码原文

if (Key_S4_Released() == 1)      /* 检测到一次完整按键（松开沿） */
{
    count_s4++;                     /* 第一步：加一 */
    if (count_s4 == 100)           /* 第二步：判断是否到达上限（注意：在加一之后！） */
    {
        count_s4 = 0;              /* 第三步：归零，从 000 重新开始 */
    }
}

（二）回绕一圈的完整旅程

（三）为什么这样写？三种写法摆在一起比

写法 分析 评价
if (count == 100) count = 0;
（本项目，且在 ++ 之后）		 每次加一后立刻检查，到 100 就拦下归零。屏幕显示范围 000~099，语义"计满一百重新来"清晰直白。 本讲采用
什么都不写，靠溢出
count++; 一路加到 255		 unsigned char 是 8 位，255 + 1 会自然回绕到 0——不加判断"居然也能跑"。但这是隐式依赖类型特性：读代码的人看不出意图，哪天变量改成 int 就直接溢出出错了。 不推荐
if (count >= 100) count = 0; 更"防御式"的写法：万一将来步长不是 1（比如连按一次加 2），== 100 可能被"跳过去"（99 + 2 = 101，判断永远不成立，再也清不了零）；>= 则必然拦截。工程上更稳健。 更稳健

（四）两个顺序问题（顺序错了，功能就错）

⚠️ 顺序雷 1：判断必须放在 count++ 之后
  • 若写成"先判断 == 100 再 ++"：count 到 99 时判断不成立，加一成 100；下一帧先判断 100 成立 → 归零，但这一帧没有加一——第 100 次按键被"吞"了，回绕点语义错乱
  • 正确顺序：先加一，再判断，再归零——与账本"先记账、再核对、再翻页"同理
⚠️ 顺序雷 2：归零必须发生在 OLED_ShowNum 之前
  • 本项目中"计数 + 限幅"整段写在显示之前，所以 100 在屏幕上一帧都不会出现，用户看到的永远是 000~099 的干净循环
  • 若把限幅判断挪到显示之后，屏幕会闪现一次 100 再跳回 000——一帧之差，体验立判
📌 计数器三要素凑齐了：账本（第三章的变量）+ 记账时机（第四章的事件）+ 限幅归零（本章的上限控制）。任何嵌入式计数类功能——按键计数、产量统计、里程累计、超时重传——骨架都是这三件套。

    OLED_ShowString(72, 32, "N=");
    OLED_ShowString(72, 48, "N=");
    OLED_Update();                 /* 把标题先刷上屏 */

    while (1)
    {
        /* ===== S4：事件计数（账本线） ===== */
        if (Key_S4_Released() == 1)      /* 完整按一次 → 返回 1 一帧 */
        {
            count_s4++;                 /* 记账：加一 */
            if (count_s4 == 100)           /* 限幅：加一之后判断 */
            {
                count_s4 = 0;              /* 归零：000 重新开始 */
            }
        }

        /* ===== S4：状态 + 次数显示（门面线） ===== */
        if (Key_S4_Down() == 1)          /* 电平式：现在按着吗 */
        {
            OLED_ShowChinese(32, 0, "按下");
        }
        else
        {
            OLED_ShowChinese(32, 0, "松开");
        }
        OLED_ShowNum(88, 0, count_s4, 3);  /* 3 位定长晒账本：000~099 */

        /* ===== S5 / S6 / S7：同样四步，坐标换 16 / 32 / 48 行 ===== */
        ...

        OLED_Update();             /* 显存整帧刷上屏 */
        DelayMs(20);              /* 20ms 扫描周期（隐式消抖） */
    }
}

（四）三个值得回味的细节

细节 为什么这么写
同一帧里 Released 和 Down 各调一次，会不会打架？ 不会。两个函数各自独立读引脚：Released 读完后更新自己的 s4_last"记忆"，Down 不看历史、只报当前电平。一个管账本、一个管门面，互不干扰。
Released 为什么放在 Down 前面？ 先记账、后显示，保证本帧的计数变化同一帧就反映到屏幕上。反过来也不会错，只是数字会晚一帧（20ms）出现——人眼察觉不到，但"先算后显"是更清晰的思路。
每帧无条件 ShowNum，会不会浪费？ 与状态文字同理：显存在 RAM 里随便涂改，一次 Update 统一上屏。3 位定长保证覆盖旧值，逻辑最简单、绝不会残留——先求正确，再谈优化（下一讲的主题！）。
📚 本讲小结：main.c 相比上一讲只多了三样东西——顶部的四本账本、循环里的记账三步（加一 / 判 100 / 归零）、每行的晒账本一行。模块化架构零改动，功能就上了一个台阶：这就是站在模块肩膀上开发的味道。

八 知识点小结与易错点

把本讲的知识点串成一张网，考试、调试、复盘都能用。

（一）知识点清单

类别 要点
电平式 vs 事件式电平式回答"现在按着吗"（按住期间每帧返回 1）；事件式回答"刚完成一次完整按键吗"（只在松开那一帧返回 1）。计数必须用事件式
计数变量unsigned char 0~255 覆盖需求且省 RAM；必须定义为全局变量（生命周期 = 程序运行期，跨帧保值）；显式 = 0 是好习惯
边沿检测事件 = 历史状态 + 现在状态的组合判断；松开沿 last==0 && now==1，按下沿 last==1 && now==0；static bit 同时提供"私有"与"记忆"两种能力
数值显示OLED_ShowNum(X, Y, Number, Length) 当黑盒拿来即用：定长 Length=3 自动补零（12→012）、覆盖旧值永不残留；Length 要罩得住最大值，坐标 X 预留 Length × 8 像素
上限控制计数三步：加一 → 判上限 → 归零，顺序不能乱；==100 在 ++ 之后判定，屏幕永远显示 000~099；>= 写法更防御式
计数器三要素账本（变量定义）+ 记账时机（事件检测）+ 限幅归零（上限控制）——一切计数类功能的通用骨架

（二）易错点排雷

⚠️ 雷 1：拿 Key_Sx_Down() 直接计数
  • 现象：轻轻一按，数字疯涨（按住 1 秒 ≈ +50）
  • 原因：电平式按住期间每帧都返回 1，数的是"持续时间"不是"次数"
  • 纠正：计数认准 Key_Sx_Released()，状态显示才用 Key_Sx_Down()
⚠️ 雷 2：Released 的 else 分支忘写 s4_last = now
  • 现象：怎么按，计数都是 0
  • 原因："按下"的状态没被记住，松开时条件 s4_last==0 永远不成立
  • 口诀：不管有没有事，账每帧都要记
⚠️ 雷 3：计数变量定义进 while 循环 / 函数里
  • 现象：计数最多到 1，永远从零开始
  • 原因：局部变量每帧重新出生、归零，账本每 20ms 被撕一页
  • 纠正：定义在 main.c 顶部（全局），或加 static（key.c 里的 s4_last 就是榜样）
⚠️ 雷 4：== 100 的判断写在 count++ 之前
  • 现象：回绕点行为错乱——第 100 次按键被"吞掉"或显示短暂异常
  • 原因：先判后加，99→100 的那一帧没被拦截，归零时机错位
  • 纠正：先加一，再判断，再归零，且整段放在显示之前
⚠️ 雷 5：ShowNum 的 Length 与实际位数不匹配
  • 现象：Length=2 时计数到 100，屏幕显示"00"（高位被截断）；Length=4 时右侧超出屏幕 127 像素，最后一位画不上
  • 纠正：Length 必须罩得住最大值，坐标 X 要给足 Length × 8 像素的空间

（三）举一反三 · 课后小练习

✏️

练习 1：实现"按下沿"计数

key.h 已声明 Key_Sx_Pressed()

模仿 Released，在 key.c 写出按下沿版本（条件 s4_last==1 && now==0），把主循环计数改成"一按下就 +1"。对比两种手感，体会"事件定义在哪一沿"是设计选择。

✏️

练习 2：上限改成 999

unsigned char 不够用了！

把上限改成 999、显示 000~999：count 变量必须升级成什么类型？判断条件改成什么？坐标 X=88 处还放得下吗？动手前先算——类型范围与像素排版的双重考点。

✏️

练习 3：加一个"清零键"

按一下 S7，全部账本清零

用 S7 的 Released 事件做"总清零"：触发时把 count_s4~count_s7 全部置 0。体会同一个事件函数既能"计数"也能"触发动作"——事件是通用的，用途看主循环怎么安排。

🚀 下一讲预告：程序的优化设计

功能已经跑起来了，但如果你盯着 main.c 看，一定会觉得哪里不对劲——S4、S5、S6、S7 四段处理代码几乎一模一样：同样的四步、同样的结构，只有变量名和坐标不同，复制粘贴了四遍。这就是传说中的"代码坏味道"（Bad Smell）。

下一讲，我们在这个能跑的版本基础上做程序的优化设计——不改功能，只改结构，行话叫重构（Refactoring）：

  • 🔁 从"四段复制"到"一个函数"：把每个按键的处理提炼成参数化的函数，代码量从 80 行缩到 20 行
  • 🧮 数组 + 循环替代独立变量：count[4] 搭配 for 循环，四个按键一网打尽，加第五个按键只需改一个数字
  • 📦 职责下沉：把"计数"逻辑收进 key 模块，main.c 进一步瘦身，只留"调度"本行
  • 🎨 显示刷新同样封装：一行调用画完"状态 + 次数"，让主循环一屏读完

从"能跑"到"优雅"，是程序员进阶的必经之路。先让它工作（Make it work），再让它优雅（Make it right）——下一讲见！
