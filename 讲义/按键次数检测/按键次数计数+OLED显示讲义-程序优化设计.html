一 项目任务与优化目标：什么是"重构"

项目三已经完整实现了"四按键状态显示 + 按下次数计数"。本项目功能与运行效果一字不变，只做一件事：把 main.c 的内部结构重新组织，让代码从"能跑"进化到"好读、好改、好扩展"。

（一）屏幕上看不出任何区别

（二）本讲的两处优化

🔁 优化一：三段式重组
主循环从"按按键分块"改为"按功能分阶段"
• 旧：S4 全部处理 → S5 全部处理 → …
• 新：状态显示 → 事件计数 → 次数显示
• 同类操作归拢，一屏读懂数据流向
⏱️ 优化二：去掉 DelayMs(20)
20ms 空转延时被注释掉
• 旧：处理 + 刷屏 + 空等 20ms
• 新：处理 + 刷屏，循环立即重启
• 扫描节拍由 OLED_Update 耗时天然形成

（三）改动清单：动手前先画边界

位置 改动
main.c 主循环结构三段式重组：状态显示段 → 事件计数段 → 次数显示段，末尾 OLED_Update
main.c 主循环末尾DelayMs(20) 注释掉（本章保留原文，便于对照回退）

计数变量定义零改动 四本"账本"照旧
🎯 什么是重构（Refactoring）：在不改变程序外在行为的前提下，调整代码内部结构，提高可读性、可维护性。行话叫 Make it work → Make it right。重构的铁律：每改一处结构，立即验证功能没变——上电按几下按键，屏幕显示与之前分毫不差，重构才算成功。

二 优化前的"代码坏味道"诊断

重构之前先"望闻问切"。项目三的 main.c 能跑，但代码里已经散发着三种经典的"坏味道"（Bad Smell）——它们不会让程序出错，却会让下一个读代码的人（包括三个月后的你自己）痛苦不堪。

（一）旧结构回放：按"按键"分块

项目三的主循环以按键为单位组织，每个按键一段、四步走完，S4 处理完才轮到 S5：

/* ===== S4 ===== */
if (Key_S4_Released()) { count_s4++; ... }   /* 计数（红） */
if (Key_S4_Down()) { ...按下... } else { ... }  /* 状态显示（蓝） */
OLED_ShowNum(88, 0, count_s4, 3);            /* 次数显示（橙） */

/* ===== S5 ===== */  同样的三步，变量名和坐标换一换 */
/* ===== S6 ===== */  再来一遍 */
/* ===== S7 ===== */  又来一遍 */

（二）三宗罪清单

1️⃣ 坏味道一：重复代码（Duplication）

四段结构 95% 相同，只有变量名（count_s4 → count_s5）和坐标（0 → 16）不同。重复不是"保险"，是"负债"：改一处逻辑（比如上限改 999）必须同步改 4 处，漏掉任何一处就是 bug。

2️⃣ 坏味道二：功能散落（Scattered Logic）

"计数"这件事发生在 4 个地方，"显示"散落在 8 个地方（4 处状态 + 4 处数字）。想确认"计满 100 清零的逻辑对不对"，你的目光要在 4 个代码块之间跳跃，还要在每次跳跃时跳过中间无关的显示代码——认知负担全压在读者身上。

3️⃣ 坏味道三：扩展成本高（Shotgun Surgery）

每加一个新按键、每改一种显示格式，都要"霰弹枪式"地改动多处。项目越长大，这种成本越高——趁项目还小，现在治，最便宜。

📌 坏味道的判断标准不是"能不能跑"，而是"改起来疼不疼"：如果每次改动都要动很多处、每次都要在脑子里"人肉拼接"散落的逻辑，就该重构了。代码是写给人看的，顺便让机器执行。

三 优化一：主循环三段式重组

药方只有一句话：把"按按键分块"改成"按功能分阶段"——同类操作归拢到一起，主循环变成清晰的三段式，正好对应数据流的"输入 → 处理 → 输出"。

（一）新结构总览

（二）三段式与数据流的对应关系

阶段 做的事 在数据流中的角色
第一阶段：状态显示 Key_Sx_Down() ×4 → 写"按下/松开" 输入 + 即时反馈：读当前电平，直接呈现，不产生新数据
第二阶段：事件计数 Key_Sx_Released() ×4 → count++、限幅 处理：把"边沿事件"沉淀为"账本数据"——唯一的写数据环节
第三阶段：次数显示 OLED_ShowNum() ×4 输出：把账本晒上屏，只读不写
收尾：OLED_Update 显存整帧上屏 物理输出：两步写的第二步，所有显示的统一出口

（三）为什么"按功能"比"按按键"更适合本项目

🎹

按按键分块 = 钢琴视角

S4 的全部 → S5 的全部 → …

适合"每个按键处理差异很大"的场景：每键一套独特逻辑，各自内聚。项目二（纯状态显示）就是这种——每键只有一个动作，怎么分都行。

🎼

按功能分阶段 = 乐谱视角

同类操作归拢成"乐章"

适合"四个按键处理方式相同、功能会持续演进"的场景：改计数规则只动第二段，改显示格式只动第三段——改动按功能发生，代码就按功能排列。

💡 判断口诀：未来改动会以什么维度发生，代码就按什么维度组织。本项目的演进方向是"计数方式、显示格式、后续控制逻辑"——全是功能维度，所以按功能分阶段；如果将来每个按键各干各的事（S4 调速、S5 换向…），再切回按按键分块也不迟。结构服务于变化，没有唯一正确答案。

（四）一个关键澄清：先后调换，结果不变？

❓ 旧版是"先计数、再显示状态"，新版第一阶段先显示状态、第二阶段才计数——会不会出问题？

不会。同一帧内，Key_S4_Down() 和 Key_S4_Released() 是两个独立函数，各自读引脚、各自维护状态：Released 内部自带 s4_last"记忆"，与 Down 的调用先后无关。唯一可感知的差别是：如果"松开事件"恰好发生在这一帧，次数数字要等到下一帧才显示 +1——主循环一轮只要几毫秒到几十毫秒，人眼完全无感。这也提醒我们：帧内阶段的先后顺序，影响的只是"晚一帧"，不影响正确性。

四 优化二：告别 DelayMs(20)——刷新即节拍

第二处优化只有一行：把主循环末尾的 DelayMs(20) 注释掉。看似大胆，实则顺理成章——因为主循环里早就藏着一位"耗时大户"：OLED_Update()。

（一）旧版一帧的时间都花在哪了

（二）为什么敢去掉：OLED_Update 才是真正的节拍器

🧮 算一笔"耗时账"

位带（bit-bang）模拟 I2C 靠 GPIO 翻转"演"时序，每一位都要好几个指令周期。OLED_Update() 要把 8 页 × 128 字节 = 1024 字节显存全部发送出去，外加每字节的应答位、每页的地址与控制字节——一次全屏刷新耗时轻松达到毫秒级。
回顾消抖的条件：扫描周期 > 抖动毛刺时长（5~10ms）。旧版里真正满足这个条件的，除了 DelayMs(20)，还有 Update 自己——两个"慢家伙"叠加，20ms 延时纯属重复保险。删掉它，节拍依旧由 Update 兜底。

（三）收益与风险，一起看清楚

✅ 收益
CPU 不再空转，循环更紧凑
• 按键响应更快（不用等空转结束）
• 屏幕刷新更勤、画面更新更及时
• 主循环少一个"人为拍脑袋"的参数
• 为将来插入更多处理留出时间余量
⚠️ 风险：隐性依赖
节拍靠 Update 的耗时兜底
• 循环周期不再是写死的 20ms，而是 "最长操作耗时"
• 哪天换高速硬件（如 SPI 屏）、或删掉显示，周期骤缩 → 抖动毛刺可能被采样进来，计数开始乱跳
• 根治方案：定时器定拍扫描（后续课程）
🔬 "能跑"和"明白为什么能跑"的差别
  • 去掉 DelayMs 后程序照样工作，很多人到此为止——但你要能说清楚它为什么还工作（Update 兜住了节拍）
  • 也要能说清楚它什么时候会不工作（显示被删掉 / 刷屏变快时，消抖失去依靠）
  • 这类"看不见的前提"叫隐性依赖：代码没有注释写明，全靠程序员心里有账。知道依赖在哪，比依赖存在与否更重要
📌 本讲的处理姿势：注释掉而不是删除 //DelayMs(20);，并在行尾保留说明——这是嵌入式开发的好习惯：优化留痕，可随时回退对照。等定时器方案上线，再删不迟。

五 优化后的 main.c 全文精讲

两处优化落地后的完整主程序。读的时候注意两件事：一是三段之间的"注释路标"，二是每段内部四个按键的整齐排列——结构感扑面而来。

（一）完整代码（带注释精讲）

/*
 * 主循环按"功能阶段"组织（三段式）：
 *   第一阶段——四个按键的当前状态显示：按下 / 松开（归在一起）
 *   第二阶段——四个按键的"按下事件"检测与计数（归在一起）
 *   第三阶段——四个按键的按下次数显示（归在一起）
 */
#include "key.h"
#include "delay.h"
#include "OLED_STC15.h"

unsigned char count_s4 = 0;   /* 四本"账本"：全局变量，定义与项目三相同 */
unsigned char count_s5 = 0;
unsigned char count_s6 = 0;
unsigned char count_s7 = 0;

void main(void)
{
    Key_Init();                /* 初始化部分与项目三完全相同，不再重复讲解 */
    OLED_Init();
    OLED_Clear();
    OLED_ShowString(0, 0, "S4:");      /* 静态标题开机只画一次 */
    OLED_ShowString(0, 16, "S5:");
    OLED_ShowString(0, 32, "S6:");
    OLED_ShowString(0, 48, "S7:");
    OLED_ShowString(72, 0, "N=");
    OLED_ShowString(72, 16, "N=");
    OLED_ShowString(72, 32, "N=");
    OLED_ShowString(72, 48, "N=");
    OLED_Update();

    while (1)
    {
        /*
         * 第一阶段：四个按键的当前状态显示（按下 / 松开）
         */
        if (Key_S4_Down() == 1)      { OLED_ShowChinese(32, 0, "按下"); }
        else                         { OLED_ShowChinese(32, 0, "松开"); }
        if (Key_S5_Down() == 1)      { OLED_ShowChinese(32, 16, "按下"); }
        else                         { OLED_ShowChinese(32, 16, "松开"); }
        if (Key_S6_Down() == 1)      { OLED_ShowChinese(32, 32, "按下"); }
        else                         { OLED_ShowChinese(32, 32, "松开"); }
        if (Key_S7_Down() == 1)      { OLED_ShowChinese(32, 48, "按下"); }
        else                         { OLED_ShowChinese(32, 48, "松开"); }

        /*
         * 第二阶段：四个按键的"按下事件"检测与计数
         * 每检测到一次"按下后放开"（Released）就计数 +1，计满 100 清零
         */
        if (Key_S4_Released() == 1)  { count_s4++; if (count_s4 == 100) { count_s4 = 0; } }
        if (Key_S5_Released() == 1)  { count_s5++; if (count_s5 == 100) { count_s5 = 0; } }
        if (Key_S6_Released() == 1)  { count_s6++; if (count_s6 == 100) { count_s6 = 0; } }
        if (Key_S7_Released() == 1)  { count_s7++; if (count_s7 == 100) { count_s7 = 0; } }

        /*
         * 第三阶段：四个按键的按下次数显示
         */
        OLED_ShowNum(88, 0, count_s4, 3);
        OLED_ShowNum(88, 16, count_s5, 3);
        OLED_ShowNum(88, 32, count_s6, 3);
        OLED_ShowNum(88, 48, count_s7, 3);

        OLED_Update();         /* 收尾：显存整帧上屏（也是本主循环的"节拍器"） */

        //DelayMs(20);           /* 20ms 扫描周期（隐式消抖） */
    }
}
💡 排版说明：讲义中为节省篇幅把单键处理压成了一行；实际工程文件里仍是展开的完整写法，逻辑一字不差。紧凑与否是排版选择，三段式才是结构本质。

（二）通读一遍：结构感从哪里来

观察点 说明
文件头注释 = 一张"地图" 开头的三段式说明先给读者全景：往下读之前就知道主循环分几段、每段干什么。结构变了，注释跟着变——注释描述结构，不是描述历史。
每段开头一段"路标注释" /* 第一阶段：… */ 是段落的标题。四个 if 整齐排列，肉眼一扫就知道"这四行干的是同一件事"——重复的规律性本身就是可读性。
第二阶段的四行结构完全同构 这为将来的"数组 + for 循环"改造铺好了路（本讲练习 3）：同构的重复，才是机器能批量处理的重复。
被注释的 DelayMs 保留在原地 优化留痕：后来者能看到"这里曾有个 20ms 延时，为什么被注释掉"，配合行尾注释即可理解原因。

（二）知识点清单

类别 要点
重构不改外在行为、只改内部结构的代码整理；铁律是每改一处立即验证功能不变；优化留痕（注释而非删除），可回退可对照
代码坏味道重复代码、功能散落、扩展成本高（霰弹枪式修改）；判断标准不是"能不能跑"，而是"改起来疼不疼"
三段式主循环状态显示（输入反馈）→ 事件计数（处理）→ 次数显示（输出）+ Update 收尾；对应数据流"输入 → 处理 → 输出"；代码按未来改动的维度组织
刷新即节拍OLED_Update 位带 I2C 发送 1024 字节显存，耗时毫秒级；只要扫描周期 > 抖动毛刺（5~10ms），消抖隐式成立
隐性依赖循环周期依赖"最长操作的耗时"——代码里看不见、全靠心里有账；换硬件或删显示时必须重新审视
注释即文档文件头注释描述结构全景（三段式地图）；段落注释做"路标"；结构变了注释跟着变

（三）易错点排雷

⚠️ 雷 1：以为去掉 Delay 消抖就失效了
  • 现象认知错误：担心按键一抖计数乱跳
  • 真相：Update 刷屏耗时毫秒级，主循环周期仍远大于毛刺时长，消抖依旧成立
  • 但要明白：兜底的是"慢刷新"而不是"运气"——这层依赖要心里有账
⚠️ 雷 2：重构时顺手加新功能
  • 现象：一边挪代码一边"顺手"改上限、改显示——出了问题分不清是重构挪坏的还是新功能写坏的
  • 纪律：改结构与加功能，永远分两次提交；每次只动一个维度，改完上电验证
⚠️ 雷 3：三段顺序随手乱换不管数据流
  • 现象：把"次数显示"挪到"事件计数"之前——功能仍正常，但计数变化要晚一帧才上屏
  • 本例无害，但习惯要养好：处理在前、显示在后，让"最新数据"第一时间上屏；将来做控制系统时，顺序将真正影响实时性

（四）举一反三 · 课后小练习

✏️

练习 1：三段各封装一个函数

State_Display() / Key_Count() / Count_Display()

把三个阶段分别提炼成函数，主循环只剩四行（三个调用 + Update）。体会"提炼函数（Extract Function）"——重构最常用的第一刀。

✏️

练习 2：亲手测出"刷新即节拍"

主循环里翻转一个 LED 引脚 + 示波器/逻辑分析仪

测出主循环真实周期，验证它 ≈ Update 刷屏耗时。再试着注释掉 Update（拿 LED 闪烁观察），看周期骤缩——亲眼看见"隐性依赖"。

✏️

练习 3：第二阶段数组化（进阶）

count[4] + for 循环

count_s4~s7 改成 count[4] 数组，第二阶段的四个 if 缩成一个 for。这是三段式铺好的路：同构的重复，正是数组化最肥沃的土壤（项目三预告过的方向）。

🚀 下一讲预告：简单的按键次数计数控制系统设计

四讲下来，计数值一直只是"晒"在屏幕上——它是展示，不是控制。下一讲，我们让计数值第一次参与决策，做一个简单的按键次数计数控制系统。

  • 🎛️ 用按键设定"目标值"：如 S4 加设定、S5 减设定，OLED 同屏显示"设定值 / 实际值"
  • ⚖️ 核心只多一个动作：if (实际值 >= 设定值)——计数值与目标值的比较，就是最简单的控制决策
  • 💡 比较结果驱动输出：点亮 / 熄灭 LED、触发蜂鸣器报警、或让系统进入某个工作状态
  • 🧩 结构继续生长：在三段式主循环上追加"第四阶段：控制决策"——上一讲搭的骨架，正好长出新肌肉

从"显示系统"到"控制系统"，只差一次比较——但这小小一步，就是所有嵌入式控制逻辑（恒温、定数计数、阈值报警）的共同起点。下一讲见！
